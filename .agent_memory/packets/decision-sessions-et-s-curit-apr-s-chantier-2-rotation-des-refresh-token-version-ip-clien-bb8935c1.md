# Sessions et sécurité après chantier 2 : rotation des refresh, token_version, IP client via cloudflared

> Depuis le chantier 2 déployé le 2026 09 24, image 232a155, migration 020 : jetons PyJWT HS256 avec jti et tv = users.…

Depuis le chantier 2 (déployé le 2026-09-24, image 232a155, migration 020) : jetons PyJWT HS256 avec jti et tv (= users.token_version) ; get_current_user refuse 401 TOKEN_REVOKED si tv < version (jeton sans tv accepté seulement tant que version 0). /v1/auth/refresh fait tourner le refresh à chaque appel : révocation atomique dans Redis (script Lua, SET NX de revoked:jti:{jti} + refresh:grace:{jti} 120 s) ; un refresh révoqué représenté après la grâce = vol présumé → token_version +1 (toutes les sessions coupées), 401 TOKEN_REUSED ; les jetons émis avant le chantier reçoivent un jti dérivé (sha256 de la partie signée) donc une vieille app qui ne stocke pas le refresh tourné est déconnectée une fois. /v1/auth/logout révoque SANS grâce et efface apns_token. POST /v1/admin/users/{id}/reset-password renvoie un mot de passe provisoire une seule fois et coupe les sessions. Redis indisponible : vérifications fail-open journalisées. IP client (app/core/limiter.py get_client_ip) : CF-Connecting-IP n'est cru que si le pair ET le dernier saut X-Forwarded-For (le $remote_addr de NPM) sont dans TRUSTED_PROXY_IPS (172.16.0.0/12 : cloudflared est en 172.23.0.3 sur net-edge, collega_net en 172.26.0.0/16) ; clients LAN (192.168.x) → dernier saut XFF ; IPv6 regroupée par /64 ; ne jamais lancer uvicorn avec --forwarded-allow-ips=*. Limites : login 5/min/IP, refresh 30/min/IP, échecs d'auth admin 10/min/IP (succès jamais limités), éval sémantique 30/min/utilisatrice, régénération 10/h/utilisatrice. ENVIRONMENT obligatoire (development|production|test, valeur exacte). Le journal d'accès uvicorn est filtré (pas de query string, UUID → <id>) ; le journal NPM du proxy host 53 garde les URI complètes. L'app ne rafraîchit défensivement (avant SSE) que si l'access expire dans < 2 min et stocke le refresh tourné avant l'access.
Evidence: 681 tests backend + app verts ; vérification prod 2026-09-24 23:05 avec un compte jetable : refresh tourné, réutilisation en grâce 200, reset → TOKEN_REVOKED, logout puis refresh → TOKEN_REUSED, webhook sans secret 401 / avec secret 200 ; aucun jeton dans les logs.
