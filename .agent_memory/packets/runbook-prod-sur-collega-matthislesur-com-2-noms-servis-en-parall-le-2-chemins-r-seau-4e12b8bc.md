# Prod sur collega.matthislesur.com : 2 noms servis en parallèle, 2 chemins réseau

> Depuis le 2026 09 26, le backend prod est collega.matthislesur.com backendBaseUrl dans collega app/lib/env.dart . L'a…

Depuis le 2026-09-26, le backend prod est collega.matthislesur.com (backendBaseUrl dans collega_app/lib/env.dart). L'ancien nom collegatest.matthislesur.com reste servi en parallèle, car les builds déjà installés l'ont en dur. Ne le retirer que quand plus aucun build ne l'utilise. Chaque nom doit figurer à 6 endroits : (a) le public hostname du tunnel Cloudflare, géré dans le dashboard (jeton) ; (b) les 3 applications Cloudflare Access (service token de l'app, collega-admin pour /admin et /v1/admin, bypass collega-webhook-revenuecat) ; (c) le proxy host NPM 53, avec le certificat wildcard *.matthislesur.com (npm-12) donc pas de nouveau certificat ; (d) Pi-hole (192.168.1.2, container binhex-official-pihole), ajout via `pihole-FTL --config dns.hosts` → 192.168.1.10 ; (e) le DNS du tailnet, généré depuis NPM par `bash /boot/config/scripts/gen-dns-tailnet.sh` (sans rien redémarrer) ; (f) le HOST du script de supervision collega-health, dont la copie installée est /boot/config/plugins/user.scripts/scripts/collega-health/script. Il y a toujours 2 chemins réseau. Depuis le LAN ou le tailnet : DNS local → NPM → collega-api-1:8000. Depuis le DNS public : tunnel Cloudflare, où tout le host est derrière Access (302 sans service token). Pour diagnostiquer : `docker logs collega-api-1` et `data/logs/proxy-host-53_access.log` de NPM. Une requête absente de ces logs n'a jamais atteint le backend.
Evidence: 2026-09-26 : LAN /health 200 sur collega ; par Cloudflare sans token, /health, /admin et /v1/colleges → 302 Access ; avec le service token (depuis le NAS), /health 200 et /v1/colleges 401 UNAUTHORIZED (backend atteint) ; webhook RevenueCat → 401 INVALID_SIGNATURE (bypass OK) ; script collega-health lan 200 et public 200.
Verified by: curl + ssh nas, session du 2026-09-26
