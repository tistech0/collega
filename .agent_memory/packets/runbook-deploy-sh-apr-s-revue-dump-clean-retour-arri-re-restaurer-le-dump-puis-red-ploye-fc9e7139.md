> Depuis ac68e5b 2026 09 24 , collega backend/scripts/deploy.sh force <sha : 1 si tistech0/collega backend:<sha existe …

Depuis ac68e5b (2026-09-24), `collega_backend/scripts/deploy.sh [--force] [<sha>]` : (1) si `tistech0/collega-backend:<sha>` existe déjà sur Docker Hub (docker manifest inspect), l'image est réutilisée telle quelle, jamais reconstruite (retour arrière rapide et fidèle) ; (2) le contrôle « aucun import en cours » abandonne (code 3, rien modifié) si Redis/Postgres sont illisibles au lieu de supposer 0 ; (3) dump pré-déploiement `pg_dumpall --clean` dans /mnt/user/appdata/collega/backups/collega_pre_<sha>_<date>.sql.gz, restaurable comme les dumps de nuit (docs/restore.md) ; (4) après succès, le sha est écrit dans /mnt/user/appdata/compose-stacks/collega/.last_deployed (source du « sha précédent ») ; seules les 5 dernières sauvegardes .env.bak-* sont gardées. Retour arrière après une migration ratée, DANS CET ORDRE : `docker compose stop api worker`, rejouer le dump pré-déploiement, puis `deploy.sh --force <sha précédent>` (l'ancienne image ne connaît pas la révision alembic plus récente). Codes : 3 = rien modifié, 5 = échec après modification. `--force` reste nécessaire tant que gh local (compte CrazyGrower) ne voit pas le dépôt privé. La config refuse d'afficher les valeurs dans ses erreurs (hide_input_in_errors) : les logs de migrate/api affichés en cas d'échec ne contiennent pas de secret.
