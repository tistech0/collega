# Génération des fiches après chantier 4 : découpage R0-R10, prompt p2 Sonnet 5, claude_usage, règle PROMPT_VERSION

> Depuis le chantier 4 déployé le 2026 09 25, image df1e4ef, migration 021, contenu de prod vidé puis à réimporter : 1 …

Depuis le chantier 4 (déployé le 2026-09-25, image df1e4ef, migration 021, contenu de prod vidé puis à réimporter) : 1) Extraction : OcrProcessor lit à part les caractères pivotés (pdfplumber upright=False, char_dir_rotated) et dédouble les lettres doublées (text_normalize.undouble). 2) Découpage (app/services/ocr/item_detector.py) : machine à états page par page, règles R0-R10 — en-têtes « Item N » tolérants (« Item 21 2 » → 212 résolu par l'ensemble K des numéros sûrs : sommaire, OBJECTIFS : N° x, ouvertures fortes), OBJECTIFS ouvre l'item, ouverture par titre connu, sections hors item (sommaire, préface, dossiers progressifs, corrigés, chapitre sans item) qui ferment l'item, pages blanches neutres, un item par numéro (réouverture = concaténation + warning), rang par objectif (pictogrammes OCR O/G/©/0 = A, Q/□/s = B). Filets : « découpage suspect » (0 item, couverture < 50 %, un item > 40 % d'un livre ≥ 100 pages, ≥ 3 en-têtes ignorés) → repli sur l'ancien découpage + warning ; 0 item après repli → job en échec « Aucun item détecté ». Rapport de découpage stocké dans generation_jobs.segmentation_report et visible dans le détail de job admin ; scripts/segmentation_report.py <pdf|fixture>. Vérité terrain des 3 collèges dans tests/fixtures/segmentation/ (textes réels privés, hors git, dans tests/fixtures/private/). 3) Texte envoyé : item_texts stocke les pages jointes par \f ; clean_for_prompt(pages) retire filigranes, (cid:N), fragments, numéros de page, en-têtes répétés (jamais les marqueurs de rang A/B/C). Empreinte item_hash toujours sur les pages brutes. RÈGLE : modifier clean_for_prompt ou le prompt impose d'incrémenter PROMPT_VERSION (GENERATION_VERSION = claude-sonnet-5:p2), sinon les générations en cache ne correspondent plus. 4) Client : claude-sonnet-5, thinking adaptatif, output_config effort medium + json_schema (flashcards[type,rang,recto,verso], insufficient_text), pas de temperature ; 0-40 fiches ; régénération max_tokens 8000 ; éval du drill Haiku 4.5 en sortie structurée. 5) claude_usage : une ligne par appel facturé (generation/regeneration/evaluation), écrite avant parsing ; coûts calculés par modèle à la lecture (Sonnet 5 2/10, Sonnet 4.6 3/15, Haiku 1/5 $/MTok). 6) Pipeline parallèle (generation_concurrency 2), persistance d'un appel payé protégée contre l'annulation, générations « texte insuffisant » jamais purgées. Mesures : 1,19 M tokens d'entrée pour les 3 collèges (≈ 5-6 € le réimport), 26-40 fiches par item au contrôle de fumée.
Evidence: 940 tests backend + app verts ; 65/65 items exacts sur les 3 collèges (fixtures et PDF réels) ; contrôle de fumée réel sur le NAS ; vidage de prod exécuté le 2026-09-25 00:03.
