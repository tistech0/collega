# Task 2 (console de pilotage) implémenté : PUT /v1/activity/{day} (app/api/v1/activity.py,

> Task 2 console de pilotage implémenté : PUT /v1/activity/{day} app/api/v1/activity.py, upsert idempotent via app/serv…

Task 2 (console de pilotage) implémenté : PUT /v1/activity/{day} (app/api/v1/activity.py, upsert idempotent via app/services/activity.py) et last_seen_at mis à jour dans login/refresh/get_me (app/api/v1/auth.py), throttlé à 10 min par activity.touch_last_seen. Deux gotchas découverts en TDD : (1) l'upsert on_conflict_do_update doit utiliser func.now() pour updated_at, pas stmt.excluded.updated_at (excluded ne reflète que les colonnes explicitement dans values(), pas les defaults Python/server_default) ; un test qui compare deux updated_at consécutifs très rapprochés (<1ms) doit vérifier `!=` et non `>`, car deux transactions Postgres sur des connexions poolées différentes peuvent voir now() dans un ordre non strictement croissant sous cette latence (jitter d'ordonnancement du backend, pas un bug, vérifié avec deux `select now()` espacés). (2) Le helper de test login_as() (tests/api_pg.py) remplace get_current_user par un `lambda: user` renvoyant un objet ORM détaché (chargé puis session fermée), différent de la session `db` de la route obtenue via Depends(get_db) : muter cet objet (ex. touch_last_seen) puis db.commit() ne persiste RIEN, car l'objet n'est pas dans l'identity map de cette session. Fix générique : appeler `await db.merge(user)` avant commit quand on mute un current_user potentiellement détaché — en production current_user est déjà attaché (dépendance partagée par requête), donc merge() est un no-op sans coût ; mais toute route qui mute current_user puis commit, testée via login_as + pg_client, doit faire ce merge ou le test échouera silencieusement (le commit réussit, mais rien n'est écrit).
Evidence: pytest tests/api/test_activity_pg.py tests/api/test_auth.py tests/api/test_auth_rotation_pg.py -q → 54 passed ; full suite 973 passed ; ruff/mypy clean ; reproduit isolément (script hors FastAPI) le comportement now() non strictement croissant sur écritures <1ms d'écart, puis monotone avec 50ms de délai.
