# Écrans de progression empilés (un push par état ImportStreaming) → rafales /status, N streams SSE, pool DB épuisé

> Repro iPhone 2026 09 21 : college import screen faisait context.push '/colleges/{ref}/import/progress' dans un ref.li…

Repro iPhone 2026-09-21 : college_import_screen faisait `context.push('/colleges/{ref}/import/progress')` dans un `ref.listen` à CHAQUE état ImportStreaming — or CollegeImportNotifier émet un nouvel ImportStreaming (copyWith) à chaque événement ocr_progress (~55 pour 355 pages) → ~55 ImportProgressScreen empilés, chacun avec son AppLifecycleListener(onResume → reconnectIfActive). Au retour premier plan : 55 GET /status dans la même seconde puis 55 streams SSE ouverts en parallèle (chaque boucle /stream ouvre une session DB toutes les 1.5 s) → `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached` et /stream en 500 sur la prod. Fix (commit 1a55430) : (1) l'écran ne pousse la progression qu'à la TRANSITION `previous is! ImportStreaming && next is ImportStreaming` ; (2) reconnectIfActive fusionne les appels concurrents via un Future en vol (`_resyncInFlight`) → un seul /status + un seul stream ; (3) _connectSse appelle `_sseClient?.disconnect()` (cancel token) avant de créer un nouveau client — annuler seulement la StreamSubscription laissait la connexion HTTP ouverte côté serveur. Tests : college_import_screen_test « n'empile qu'UN écran… » (find.byType(_ProgressStub, skipOffstage: false) → 1) et college_import_notifier_test « reconnectIfActive appelé N fois en parallèle → UN seul /status ». Leçon : toute navigation déclenchée dans un ref.listen sur un state qui se ré-émet doit comparer avec `previous`. Le resync avec backoff décrit dans le packet précédent reste valable et complète ce fix.
Evidence: Logs NAS 13:53-13:55 : rafales de 13-30 GET /status par seconde depuis 192.168.1.128, puis /stream 500 avec traceback QueuePool ; après force-quit de l'app, plus d'erreur. flutter test test/features/colleges : 47 passed (2 nouveaux tests rouges puis verts).
